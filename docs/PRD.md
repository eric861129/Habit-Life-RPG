# Habit Life RPG PRD

版本：Chapter 3 Blueprint  
狀態：MVP 產品藍圖  
對應書稿：第 3.1 節「PRD 產品需求文件」

## 1. 摘要總結

`Habit Life RPG` 是《左手藍圖，右手魔法：用文件驅動 AI 開發》的主線範例專案。產品目標是把習慣養成轉換成 RPG 練等循環，讓使用者在完成每日習慣後，立即獲得金幣、經驗值與等級成長的回饋。

這份 PRD 是後續 AI 建築團隊的最高產品依據。任何後端、前端、測試或部署實作，都必須回到本文件確認「這個功能是不是 MVP 必要內容」、「規則是否由伺服器端判定」、「是否超出本書主線範圍」。

## 2. 產品願景

讓使用者把自我提升視為一場可持續的角色養成旅程。

使用者不只是完成待辦事項，而是在累積角色經驗、取得金幣、避免 HP 扣減，並透過數值回饋看見自己的長期成長。

## 3. 目標使用者

- 想培養固定習慣，但容易因缺乏即時回饋而中斷的人。
- 喜歡 RPG、等級、經驗值、金幣等遊戲化語言的人。
- 想學習「文件驅動 AI 開發」流程的讀者與開發者。

## 4. MVP 範圍

### 4.1 本書主線會實作

- 使用者可以登入系統。
- 使用者可以看到自己的習慣清單。
- 使用者可以對單一 habit 執行每日打卡。
- 打卡成功後，後端負責結算經驗值、金幣與等級。
- 系統會阻止同一個 habit 在同一天重複打卡。
- 系統會保留懲罰機制的 MVP 規則，讓未打卡行為能扣減 HP。
- 前端會顯示角色狀態、habit 清單、打卡結果與升級提示。

### 4.2 只規劃，不在本書主線完整實作

- BOSS 戰系統。
- 屬性配點，例如力量、智力、敏捷。
- 複雜裝備與商店系統。

### 4.3 留給讀者延伸練習

- 番茄鐘專注模式。
- 看板式 habit 管理。
- 月曆檢視與長期趨勢圖。
- 進階成就、任務鏈與社群排名。

## 5. 核心玩法

1. 使用者登入後進入首頁。
2. 首頁顯示角色狀態與今日 habit 清單。
3. 使用者完成某個 habit 後點擊打卡。
4. 前端呼叫 `POST /api/v1/habits/{habit_id}/checkin`。
5. 後端驗證使用者身分、habit 歸屬與當日打卡狀態。
6. 後端計算獎勵並更新資料。
7. 前端顯示成功提示、更新經驗值與金幣。
8. 如果經驗值達到升級門檻，前端顯示升級慶祝狀態。

## 6. 產品規則

### 6.1 伺服器權威

所有會影響角色數值的判定都必須在後端完成。前端只能呈現結果，不可自行決定經驗值、金幣、等級或 HP 變化。

### 6.2 同日不可重複打卡

MVP 以 `Habits.LastCheckIn` 記錄最近一次打卡日期。當使用者對同一個 habit 重複送出同日打卡請求時，後端必須拒絕。

### 6.3 Habit 歸屬驗證

使用者只能打卡自己的 habit。若 `habit_id` 存在但不屬於目前登入使用者，後端必須拒絕。

### 6.4 等級成長

MVP 使用可解釋、可測試的等級公式：

```text
RequiredExp = Level^2 * 100
```

第 5 章可以先以固定打卡獎勵跑通主循環，第 6 章再用測試鎖住邊界條件。

### 6.5 懲罰機制

系統保留未打卡扣減 HP 的設計。MVP 不追求複雜數值平衡，而是先確保規則集中在後端，未來可以擴充為更完整的懲罰與恢復機制。

## 7. 早期資料概念

第三章只定義產品語言，不正式設計資料庫。第 4 章才會把它轉成 ERD 與 API Spec。

### 7.1 Users

代表使用者與角色狀態。

預期包含：

- 使用者識別欄位。
- 帳號資訊。
- 密碼雜湊。
- 目前等級。
- 目前經驗值。
- 目前金幣。
- 目前 HP。

### 7.2 Habits

代表使用者想培養的習慣。

預期包含：

- habit 識別欄位。
- 所屬使用者。
- habit 名稱。
- habit 描述。
- 獎勵設定。
- 最近一次打卡日期 `LastCheckIn`。
- 啟用狀態。

## 8. 主 API 契約

本書主線優先鎖定以下 API：

```http
POST /api/v1/habits/{habit_id}/checkin
```

此 API 必須支援：

- 驗證登入使用者。
- 驗證 habit 是否屬於該使用者。
- 檢查同日是否已打卡。
- 結算經驗值、金幣與等級。
- 回傳前端更新畫面所需的角色狀態。

詳細 request / response schema 會在第 4 章 API Spec 中定義。

## 9. 技術路線

### 9.1 本機 MVP

- Backend：FastAPI。
- Database：SQLite。
- Testing：Pytest。
- Frontend：React + Vite + Tailwind CSS。

### 9.2 雲端部署

- Database：Azure SQL。
- Backend Hosting：Azure App Service 或等價可部署平台。
- Frontend Hosting：Azure Static Web Apps。

第三章不建立這些程式碼，只把路線寫清楚，讓後續章節按文件施工。

## 10. 非功能性需求

### 10.1 安全性

- 密碼必須雜湊後儲存，不得保存明文密碼。
- 所有會讀寫使用者資料的 API 都必須驗證身分。
- 不得把真實 secret、API key、connection string 或 token 提交到 Git。

### 10.2 可測試性

- 主要商業規則必須能用 Pytest 驗證。
- User Stories 的驗收標準會作為第 6 章測試案例來源。
- 重複打卡、habit 歸屬錯誤、成功結算都必須有測試。

### 10.3 可擴充性

- 前後端分離。
- API 使用穩定版本路徑 `/api/v1`。
- MVP 命名統一使用 `habit` / `habits` / `habit_id`。

### 10.4 可讀性

- 文件與程式碼要能讓讀者沿著章節理解。
- 不在早期章節提前塞入後面章節完整成品。

## 11. 風險與因應

| 風險 | 影響 | 因應 |
| :--- | :--- | :--- |
| MVP 範圍膨脹 | 讀者被複雜功能淹沒 | 將 BOSS、配點、番茄鐘等功能列為延伸，不進入主線實作 |
| 前端自行計算獎勵 | 使用者可竄改分數 | 所有數值結算集中在後端 |
| 重複打卡刷分 | 破壞遊戲化公平性 | 使用 `Habits.LastCheckIn` 做同日檢查 |
| 文件與程式碼不同步 | AI 後續施工偏離 | 每章更新文件、測試與 release note |
| 真實秘密外洩 | 安全與出版風險 | `.env` 不提交，`.env.example` 只保留假值 |
